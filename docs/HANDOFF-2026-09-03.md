# Handoff - 3 September 2026

Written at the end of a session that began with "my brave doesnt open .... not
even the psw pop up appears" and ended with a rebuilt recovery path. If you are
picking this up cold, read the incident first: the design decisions afterwards
only make sense in its light.

---

## 1. The incident

Brave would not open and no passphrase prompt appeared. **Two independent
faults**, both confirmed on the live machine.

### Fault A - a browser update silently took the lock off

`C:\ProgramData\Microsoft\Windows\Start Menu\Programs\Brave.lnk` had:

```
Target : ...\Brave-Browser\Application\brave.exe     <- should be wscript.exe
Args   : "C:\Program Files\BraveLocker\scripts\BraveLockerLauncher.vbs"
```

Brave's updater rewrites `TargetPath` and **leaves `Arguments` untouched**.
Timestamps pinned it: the shortcut, `Application\SetupMetrics`, and
`Application\152.1.94.119` were all written within the same second (09:26:4x).

Consequences, both bad:

- clicking Brave ran `brave.exe` directly, so the launcher never ran and no
  passphrase was ever asked for - **the lock was off and nothing said so**
- anything checking the shortcut's *arguments* still saw the locker's `.vbs` and
  concluded it was locked. Only the target tells the truth.

### Fault B - a dangling volume mount point

`...\Brave-Browser\User Data` was a reparse point to
`\??\Volume{82f7ecbf-...}\`, while `Get-DiskImage` reported `Attached: False`.
Enumerating the path failed with *"Could not find a part of the path"*, so Brave
could not open its own profile directory and died on launch.

It got there because a session ended without a dismount (`response.json` still
recorded the *mount* from the previous day; no dismount was ever written).

**This was a permanent trap.** The only code that removes that mount point is
`Remove-BraveLockerVaultAccessPath` -> `Remove-PartitionAccessPath`, which works
*through the partition* - and there is no partition once the vault is detached.
The launcher reported "something is already mounted... restart the PC", advice
that could never work. No restart removes a mount point nothing owns.

### Two traps found while fixing it

- `fsutil reparsepoint delete` is **not** usable here. It opens the target
  before deleting and fails with "cannot find the path specified" - which is
  precisely the condition being repaired. Use `mountvol /D` (needs admin), with
  `[System.IO.Directory]::Delete` as the unelevated fallback.
- **`Uninstall-BraveLocker.ps1` would have destroyed the user's data.** It
  restores the profile from `User Data.premigration` (a pre-migration copy) and
  then *deletes the vault* - throwing away everything done in the browser since
  setup. It is correct only immediately after a setup you regret. This is why
  `Unlock-BraveLockerPermanently.ps1` now exists.

## 2. The design principle everything else follows from

The user's question was the sharp one: *"how are you sure it will repair? can
you calculate all the problems that may occur?"*

**No, and the code no longer pretends otherwise.** Every fault above was found
on a machine that had already broken. Recovery built only from anticipated
faults is worth exactly as much as the guesswork behind it.

So the guarantee was moved somewhere that does not depend on foresight:

> **Clicking the browser icon has exactly two acceptable outcomes: the
> passphrase box appears, or a browser opens. Never silence, and never advice
> that cannot work.**

What makes "nothing happens" possible as a *class* is that the launcher runs
with no console, so an unhandled error is invisible. Wrapping everything turns
every unanticipated fault into a dialog - without anyone having to know what the
fault was.

## 3. What changed

### New files

| File | Purpose |
|---|---|
| `scripts/Repair-BraveLocker.ps1` | Self-elevating one-click repair: clears stale mount points, re-points hijacked shortcuts, registers the guard, installs the card. |
| `scripts/Unlock-BraveLockerPermanently.ps1` | The escape hatch. Copies the **current** profile out of the vault, restores the original shortcut, stands the locker down. **Never deletes the vault.** |
| `scripts/Invoke-BraveLockerShortcutGuard.ps1` | Runs at logon, re-locks any shortcut a browser update hijacked. |
| `docs/EMERGENCY-CARD.md` | Four escalating recovery levels, ending with opening the vault on any Windows PC with no Browser Locker at all. Pure ASCII (see below). |
| `tests/manual/Test-LauncherNeverDeadEnds.ps1` | Breaks the launcher four ways, asserts each produces a way out. |
| `tests/manual/Test-EscapeHatch.ps1` | Builds a real BitLocker vault and runs the escape hatch against it. |

### Changed behaviour

- **`Start-BraveLocked.ps1`** - restructured around the contract above. Whole
  body wrapped; `Show-BraveLockerLastResort` depends on *nothing* (not even the
  module, since a module that will not import is one of the things that can go
  wrong) and **logs before it shows**, because a dialog can fail or block.
  Dead ends now call `Resolve-BraveLockerDeadEnd`, which offers Retry /
  Open-without-the-lock / Turn-the-lock-off.
- **`MountPoint.ps1`** - `Test-BraveLockerStaleMountPoint` distinguishes a
  *stale* mount point from a *live* one (can anything be read through it?).
  `Initialize-BraveLockerMountFolder` clears stale ones and reports
  `ClearedStaleMountPoint`; if it cannot, `StaleMountPointStuck` says so rather
  than advising a useless restart.
- **`Shortcuts.ps1`** - `Test-BraveLockerShortcutIsLauncher` (checks the
  **target**, never the arguments), `Get-BraveLockerHijackedShortcut`,
  `Install-BraveLockerRescueItems`.
- **`Elevation.ps1`** - `Register-BraveLockerShortcutGuardTask` /
  `Unregister-...`, task `BraveLocker-ShortcutGuard`, at-logon, RunLevel Highest.
- **`Ui.ps1`** - `Show-BraveLockerRecoveryChoice`, a form (not MessageBox)
  because each choice needs a sentence explaining its consequence.
- **`Vault.ps1`**, **`Invoke-BraveLockerVaultTask.ps1`** - carried over from
  earlier in the session: wrong-passphrase is now distinguished from every other
  unlock failure by HRESULT `0x80310027`, so a broken mount no longer accuses a
  correct passphrase or burns a cooldown.

### Two bugs the tests caught

- The installed card rendered as `a EUR"` mojibake in Notepad - UTF-8 with no
  BOM read as ANSI. The card is now folded to **pure ASCII** on install and at
  source, and a test asserts zero bytes above 127. It is the one document that
  must be readable when everything else has failed.
- `.Replace([char], '...')` binds `String.Replace(char, char)` and throws.
  Replacements are string-to-string now.

from the recovery dialog and the card. A one-click "remove my security" item is

## 5. Verified vs not - read this before trusting anything

### Verified

- 203 Pester tests pass.
- **Shortcut guard, end to end:** the shortcut was hijacked exactly as Brave's
  updater does it, the guard detected and repaired it, and logged the fix.
- **Launcher never dead-ends:** corrupt config (unanticipated - hit the
  catch-all), config with no mount path, cooldown lockout - all three produced a
  recovery dialog. Broken module produced a dialog plus a durable log record.
- **Mounting a VHDX requires admin** - measured, not assumed: a standard user
  gets *"A required privilege is not held by the client."* The card says so.
- The live repair itself (stale mount point cleared, shortcut re-pointed).

### NOT verified - the honest list

1. **`Unlock-BraveLockerPermanently.ps1` has never been run end to end.** It is
   the escape hatch, and it is unproven. `tests/manual/Test-EscapeHatch.ps1` was
   written to prove it against a throwaway encrypted vault but **had not been
   executed when the session ended**. Run it before relying on the script.
2. Nobody has clicked the recovery dialog's buttons by hand. The three choice
   paths were exercised through a stub, not a mouse.
3. The BitLocker unlock prompt on the *real* vault was never observed - the
   vault was in use throughout.
4. Everything remains verified on one machine, one browser, one person. See
   `docs/VM-TEST-PLAN.md`, which was already honest about this.

## 6. Next steps

1. **Run `tests/manual/Test-EscapeHatch.ps1` from an elevated PowerShell.** It
   is self-contained: builds its own encrypted VHDX and fake profile, touches
   nothing real, cleans up after itself. This is the highest-value outstanding
   task - item 1 above.
2. Click through the recovery dialog by hand once, on each of the three
   choices.
3. Consider whether `Uninstall-BraveLocker.ps1` should refuse outright once
   `PreMigrationPath` is stale, rather than relying on the card to warn people
   off it.
4. The user asked, if a separate rescue tool were built, that it be "a whole app
   which will be the locker and everything else". That was declined in favour of
   making the launcher itself incapable of dead-ending - less code, less to
   break, and it does not help if the rescue app is the broken thing. If a
   unified app is still wanted it is a clean separate project on top of this.
5. `User Data.premigration` is still on disk: a second, **unencrypted** copy of
   the profile from before the lock. It is a safety net and also an unprotected
   copy of their browsing data. Worth a decision.

## 7. Conventions worth keeping

The comments in this codebase explain *why*, usually by naming the thing that
went wrong. That is deliberate and it earned its keep this session - the comment
on `Get-BraveLockerVaultPartition` about `Get-Disk` rejecting a null `-Number`
described the exact mechanism that had destroyed the evidence in
`response.json`. Keep writing them that way.

Two specific rules the code now depends on:

- Judge a shortcut by its **target**, never its arguments.
- Never report a BitLocker failure as a wrong passphrase unless it is
  `0x80310027`. Anything else is a different problem with a different fix, and
  blaming the passphrase sends someone hunting for a typo that is not there.
